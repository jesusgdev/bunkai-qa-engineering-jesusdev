Flujo Jira: Backlog → Shift-Left QA → Estimation → Ready For Dev → In Progress → In Review → Ready For QA → In Testing → Tested → Closed

El pipeline QA tiene 7 etapas numeradas del 0 al 6. El Stage 0 es pre-sprint (shift-left), los Stages 1-3 son el sprint testing por ticket, y los Stages 4-6 son post-QA (documentación, automatización, regresión). El flujo Jira muestra todas las transiciones de estado que un ticket puede recorrer.
Stage 0 — Pre-Sprint

Shift-Left Testing

Refinamiento AC en lote antes del sprint. Detecta gaps, ambigüedades y riesgos ANTES de que Dev escriba código.

¿Qué hace?

  • Refina ACs de Stories en Backlog
  • Spotting de gaps y ambigüedades
  • Draft de ATP (Acceptance Test Plan)
  • Transiciones: backlog → shift_left_qa → estimation
  • Agrega label shift-left-reviewed

Comandos Jira

# Buscar Stories en Backlog
acli workitem search --type Story --status Backlog --fields summary,status,labels --json

# Transicionar a Shift-Left QA
acli workitem transition BK-XXX "Shift-Left QA"

# Agregar label
acli workitem edit BK-XXX --add-label shift-left-reviewed
El Stage 0 es pre-sprint. Se ejecuta en lote sobre varias Stories del Backlog. El objetivo es refinar los criterios de aceptación antes de que el equipo de desarrollo empiece a trabajar. Se agregan labels para que sprint-testing pueda hacer short-circuit de las primeras fases.
Stage 1 — Sprint QA

Planning (Sprint Testing)

Preparación del ticket: sync desde Jira, lectura de ACs, exploración de código, authoring del ATP.

Pasos

  1. Sync ticket: bun run jira:sync-issues get BK-XXX
  2. Leer ACs y contexto de .context/PBI/
  3. Explorar código relevante
  4. Author ATP → escribir en Jira (campo o comment)
  5. Transicionar: Ready For QA → In Testing

Short-Circuit

Si el ticket tiene label shift-left-reviewed y tiene <30 días, se saltan las fases 1-3 de planning y se va directo a ejecución. 

# Comando para correr sprint-testing
/sprint-testing BK-XXX
Stage 1 es planning. Se sincroniza el ticket desde Jira, se leen los criterios de aceptación, se explora el código relevante y se escribe el ATP. Si el ticket ya fue shift-lefted hace menos de 30 días, se puede hacer short-circuit.
Stage 2 — Sprint QA

Execution (Trifuerza)

Ejecución exploratoria: smoke test + trifuerza (UI / API / DB) + filing de defectos.

🖥️

UI

Playwright MCP o /playwright-cli para exploración visual y interacción con el browser.

🔌

API

OpenAPI MCP o curl para validar contratos, respuestas y errores de endpoints.

🗄️

DB

DBHub MCP para validar estado de datos, transacciones y consistencia.

Si hay defecto: Crear Bug en Jira → transicionar a Open → file evidence → linked al Story.

Stage 2 es ejecución. Se usa el trifuerza: UI (Playwright), API (OpenAPI/curl), y DB (DBHub). Si se encuentra un defecto, se crea un Bug en Jira con evidence y se linkea al Story original.
Stage 3 — Sprint QA

Reporting (ATR + Bugs)

Resultados: ATR (Acceptance Test Results), bug reports, transiciones de estado, handoff a Stage 4.

Sin Defectos ✅

  1. Escribir ATR en Jira
  2. Transicionar: In Testing → Tested
  3. Handoff a /test-documentation
  4. Transición final: Tested → Closed

Con Defectos 🐛

  1. Crear Bug en Jira con evidence
  2. Link al Story: blocks o is blocked by
  3. Dev fixea → transición Open → In Progress → Resolved
  4. QA re-testea → Resolved → Closed
  5. Story continúa: In Testing → Tested → Closed
Stage 3 es reporting. Si no hay defectos, se escribe el ATR y se cierra el ticket. Si hay defectos, se crean Bugs con evidence, se linkean al Story, y se espera a que Dev los resuelva antes de continuar.
Escenarios de Defectos

Bug vs No Bug — Todos los Caminos

Escenario A: Sin Bug

Ready For QA → In Testing → Tested → Closed

Handoff a /test-documentation para TCs en TMS.

Escenario B: Bug Bloqueante

Story bloqueado → Bug Open → Dev fix → Resolved → QA re-test → Closed

Story queda en In Testing hasta que todos los Bugs estén Closed.

Escenario C: Bug No-Bloqueante

Story puede cerrarse con bug menor → Bug se deja como Open para siguiente sprint.

Se documenta en ATR como known issue.

Escenario D: Re-test Post-Fix

Resolved → QA re-testea → Pass: Closed / Fail: re-open Open

Cada re-test se documenta con evidence nueva.

Cuatro escenarios principales: sin bug (flujo limpio), bug bloqueante (story espera), bug no-bloqueante (se documenta y pasa), y re-test post-fix (ciclo de verificación).
Stage 4 — Post-Sprint

Test Documentation & ROI

Documentar TCs en TMS (Jira/Xray), calcular ROI, decidir Candidate / Manual / Deferred.

Candidate

Alimenta /test-automation. ROI alto — se automatiza.

Manual

Terminal. Requiere intervención humana cada vez.

Deferred

Terminal. No se automatiza por bajo ROI o complejidad. 

# Ejecutar documentación de tests
/test-documentation BK-XXX
Stage 4 es documentación. Se crean Test Cases en TMS (Xray), se calcula ROI, y se decide si cada TC es Candidate (automatizable), Manual (terminal) o Deferred (no se hace).
Stage 5 — Post-Sprint

Test Automation (KATA)

Escribir tests E2E + API con Playwright + TypeScript siguiendo la arquitectura KATA.

Pipeline

  1. Plan: diseño del ATC (Acceptance Test Case)
  2. Code: escribir en tests/components/
  3. Review: KATA compliance check
  4. Registrar fixture en test file

Arquitectura KATA

TestContext → config, faker, utils

ApiBase / UiBase → HTTP / Playwright

YourApi / YourPage → ATCs live here

TestFixture → dependency injection 

# Ejecutar automatización
/test-automation BK-XXX

# KATA compliance check
bun run kata:manifest:check
Stage 5 es automatización. Se escriben tests E2E y API usando la arquitectura KATA (TestContext → Base → Domain → Fixture). Cada ATC es un mini-flow completo y atómico.
Stage 6 — Pre-Release

Regression & GO/NO-GO

Ejecutar suite de regression via CI, clasificar failures, decidir release readiness.

Clasificación de Failures

  • REGRESSION — Break real, nuevo
  • FLAKY — Falla intermitente
  • KNOWN — Bug documentado
  • ENVIRONMENT — Infra no test
  • NEW TEST — TC nuevo fallando

Veredicto

GO — 0 regressions, pass rate ≥ threshold
CAUTION — regressions menores, workarounds
NO-GO — regressions críticas sin fix 
# Ejecutar regresión
/regression-testing

# Resultados en Allure
bunx allure open ./allure-results
Stage 6 es regresión. Se ejecuta la suite de regression via CI, se clasifican los failures, y se emite un veredicto GO/CAUTION/NO-GO antes del release.

  --type Automated
