Open by framing this as a strategic plan, not a list of test cases. The key message: Bunkai's risk is not one isolated page or endpoint. The product succeeds only when auth, workspace scope, imported requirements, ACs, and ATCs stay consistent as one chain. Tell the audience that this deck compresses the master test plan into the decisions QA should make first: what must be tested, why it matters, and what should not be allowed to ship without evidence.

This is the central mental model for the whole presentation. A test can pass at the page level while the business chain is still broken. For example, an ATC can save successfully but be linked to the wrong AC. A Jira import can be marked completed but place stories into the wrong module. A PAT can authenticate but see data outside its workspace. The strategy is to test the chain end to end around each risk.

04 / critical-flow

Critical 1: identity and tenant safety

What can break

  • Viewer mutates via API
  • PAT bypasses workspace RLS
  • Mixed cookie + bearer uses wrong principal
  • Non-member infers data from errors

What QA must prove

  • Role matrix holds in UI and API
  • Cross-workspace reads stay hidden/forbidden
  • PAT and session produce same tenant boundary
  • Service-role actions are pre-authorized
If this layer fails, every downstream test result becomes untrustworthy.
This slide is about the most important security and quality risk. Explain that the system is workspace-scoped by design. The release cannot be considered safe unless viewer, member, admin, owner, session, and PAT behavior all line up with the same tenant boundary. The service-role exception is not automatically bad, but it must be tested negatively route by route because it intentionally bypasses RLS after app-level authorization.

Make it clear that enqueue success is not import success. The import returns quickly, then the worker does real work later. A release check must prove that completed jobs really created the expected stories and ACs, failed jobs explain why they failed, duplicate active jobs are blocked, and unknown components do not silently hide structure problems.

08 / access-risk

Every token test needs both happy-path access and replay/wrong-user rejection.

    
Tie PATs and invites together as secret-like flows. They are different business actions, but the risk pattern is similar: raw values are shown once, tokens can be replayed, and access must be bounded. For PATs, the key risk is automation access with scopes and RLS parity. For invites, the key risk is wrong-email acceptance, replay after revoke or expiry, and role escalation.

09 / silent-killers

The most undertested risk: invisible side effects

Import workerCan stall after enqueue
ADF extractionCan lose requirement meaning
Module cascadeCan leave active orphans
AC rebalanceCan duplicate positions
ATC RPCCan partially replace children
Audit writesCan silently fail
Manual migrationsCan drift by environment
No APM/CICan ship regressions unseen
Silent killers are where the plan becomes especially valuable. These processes may not have a direct visible failure at the moment the user clicks. The user can enqueue import, save an ATC, move a module, or revoke a PAT, and the UI can appear fine while the DB side effect is wrong. Recommend synthetic probes, read-only DB validation, status polling, audit assertions, and release-time schema checks.

OpenAPI/ScalarStale docsValidate via generated spec/source

The main point is that dependency failures should not create ambiguous product behavior. Supabase failures should not leak data or mutate partially. Jira failures should not look like successful imports. Vercel worker issues should be visible through import status. OpenAPI issues should not block the app, but they do affect automation reliability. For each integration, QA should define what still works and what must hard-fail.

Close by making the deck actionable. Do not hide the gaps. The plan is valuable because it separates verified risk from unknowns. The most actionable drift is project-config: branch and migration count should be corrected or confirmed. Product gaps should become discovery or shift-left questions. Runtime gaps should shape regression and release readiness. The next step is to turn priorities into TMS cases, then automate selected high-ROI KATA flows, then run regression evidence. End with the rule: no release confidence without tenant boundary, ATC provenance, and Jira import evidence.
